# B3b：完整 Path × PID 目标速度候选的覆盖审计

目的：在训练新的 joint scorer 前，检查现有候选空间里是否真的有可能被执行、且不需大幅牺牲进度的避碰替代。沿用 held-out 的 5000 帧、B2 corridor checkpoint 产生的 6 条原始 Path 和 4 条局部偏移 Path；不重新提取模型特征，也不训练。

运行：

```bash
/mmu_mllm_hdd_3/liuzihan08/miniconda3/envs/lead/bin/python scripts/p4/audit_b3b_pid_joint_coverage.py
```

实验定义：保留当前选中的 Path/目标速度作为 baseline。其他动作是保持当前目标速度，或减 0.5、1、2 m/s，以及停车；不考虑加速。每个目标速度先通过生产代码中的 `get_throttle` 决策和近似车辆纵向动力学，得到 2 秒内每 0.25 秒的路程，再由限角速度 30°/s、前瞻 2 m 的简化路径跟踪器生成 ego 位姿。对 GT future actors 的包围盒做 SAT 碰撞判断。候选必须满足导航方向的 GT 专家路径代理、预测 Visual Intent corridor、Path 有效、2 秒行程不超过 Path 长度、相对 baseline 不损失超过 2 m 进度、跟踪误差不超过 1 m。对 corridor cost 检查 0.1 和 0.3 两档。原始安全帧始终保持 baseline，不进行重选。

预设的“值得继续开发候选打分器”门槛：至少 50 个原始碰撞帧；扩大后的候选能救至少 20% 原始碰撞帧；其中至少 10 帧是原有 6 条 Path 无法救、只靠新增局部 Path 救回。这仅是候选覆盖门槛，**不是**部署或闭环收益门槛。

结果（5000 帧）：原始预测轨迹 175 帧碰撞。corridor≤0.1 时，同一 Path 改目标速度救 45 帧；原有 6 Path×速度救 46 帧；加入 4 条局部 Path 后救 78 帧，新增 Path 独有收益 32 帧（22 条 route，其中 23 帧无需改变目标速度）。corridor≤0.3 时分别为 46/47/84 帧，新增 Path 独有收益 37 帧。严格档中，扩大候选的 78 帧分布于 32 条 route；72 帧所选目标速度仍大于零。以严格档计 45% 的原始碰撞帧存在某种可行替代，但只占全部采样帧 1.56%。两档均过上述*覆盖*门槛。

原始轨迹本身在简化跟踪器下有 282/5000 帧的最大偏差超过 1 m；在 175 个原始碰撞帧中只有 127 帧满足该跟踪误差阈值，而 78 个救回帧中 72 帧的原始轨迹也满足。若仅看这一较可信的子集，则是 72/127 帧有替代，但不能把这个条件化比例外推到全部闭环状态。

原 B3b 几何插值版本报告 164 个原始碰撞帧，与本次 175 帧只有 100 帧重合；这是 rollout 模型改变后的标签，不宜把两次救回计数直接相减当作算法增益。

关键观察：原有多模 Path 几乎没有增益（严格档只多 1 帧），新构造的局部 Path 是覆盖提升的主要来源；因此后续不要只给原先 6 条 route 加 velocity scorer。新增局部 Path 的收益需要进一步审计是否真的位于可驾驶区域，并检查偏移量是否引起新的闭环轨迹误差。

限制：这是使用 **GT future actors** 和 **GT expert direction proxy** 的 oracle；纵向车辆动力学和横向跟踪器都是近似的，不是实际 CARLA/LEAD 的完整 PID 与反馈控制。候选只在原始不安全帧计算 GT 碰撞，不能把这里的最佳候选直接作为闭环策略，也不能据此估计 false switch。不同前向批次的原始目标速度并不完全一致，脚本只从 B3b 原始档案读取目标速度，另外按精确帧 key 从特征缓存读取传感器当前速度。

下一步：先验证新增局部 Path 的道路占用/可跟踪性；若成立，改为对完整可执行候选轨迹打 scene-conditioned 多维度分数（安全、道路可行性、任务一致性、进度/舒适性），保留当前 baseline 的执行优先级；做 held-out 排序与校准，随后 shadow、小范围配对闭环，最后才是 220 route。不要直接用 oracle 选择部署。
